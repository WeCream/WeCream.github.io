这个主页是怎么来的：一次「扒站」改造记录

2026-11-06 · 前端 · GitHub Pages · 像素风

这个主页不是从零画的：它最初是别人的一个像素风个人主页，我把整站扒下来，换成自己的名字，再把作者的全部私人内容清空，最后推到 GitHub Pages。整个过程花了不到一天，但有几个地方挺坑，记下来。

一、先确认扒的是不是「那一页」

第一件容易搞错的事：一个站点里页面很多，你在浏览器里右键另存的那个 index.html，很可能是子页而不是主页。我手上那份就是「工坊」子页，里面引用的全是 ../font.css、../assets/theme.css 这种上一级路径 —— 单独放在一个文件夹里，样式和导航全断。

判断办法很直接：看它引用的相对路径是往上一级的，还是本站根目录的。真正的主页应该只引用 ./assets/ 这一层。

另一个确认手段是查标题和大小：主页往往是 500 KB 以上的单文件，子页通常几十 KB。

二、把依赖闭包补齐，别猜

这类「单文件自重」的页面，CSS 和大部分 JS 都内联在 HTML 里，看起来很好搬。但真正跑起来需要的还有：

  • 字体：font.css 里 @font-face 引用的 woff2。不下载，页面会悄悄回退到系统字体，像素风就没了。
  • importmap 指向的模块：three.module.js 这类。它会继续去引 three.core.min.js，两者必须在同一目录，路径不能随意改。
  • 异步 import 的入口：页面末尾的 import('./assets/toon/main.js') 下面还有一整张 import 图，要递归抓完，一个 404 就是黑屏。

我的做法是写个递归下载器：从入口文件里正则出所有 import / from，用 相对路径归一化（split('/') 处理 . 和 ..）拼出下一层的 URL，循环到没有新文件为止。这一步抓了 15 个文件、约 1.1 MB，零 404。

踩坑提醒：不要用绝对路径 API（比如 .NET 的 GetFullPath）去解析网页里的相对 import —— 它会把路径拼成你本机的绝对目录，然后整批 404。

三、三维场景是程序化建模，不用抓贴图

确认这一点能省很多事：如果 main.js 里只有渲染器、相机、光照和 buildSky / makeBookshop 这类函数，没有任何运行时拉取 .glb / .png 的痕迹，那这 15 个 JS 就是全部依赖，不需要再补模型和贴图。

四、替换身份，但别忘了「凭据」和「计数」

改名是最简单的部分，用全局替换就行。真正需要单独处理的，是那些不该跟着版式一起搬过来的东西：

  • 留言板的 giscus 凭据：data-repo / data-repo-id / data-category-id 是原作者的仓库。照搬过去，等于你的页面把评论写进别人的 Discussions。必须换成自己的，或者先摘掉。
  • 访问计数、RSS、友链、个人主页链接：这些指向的都是原作者的账号，留着就是错的。
  • 私人内容：书影音馆藏、歌单、照片、文章，这些既是数据也是隐私，骨架版里应该清空而不是保留。

清空的时候有个技巧：只删数据、不删容器。很多块级 JS 是 querySelector + 直接改属性的写法，把容器删了就会抛错误，把内容清空（或者把 JSON 换成空数组）则是安全的 —— 页面自己会显示空态。

五、部署：仓库名就是域名

GitHub Pages 的根站要求仓库名必须叫 <用户名>.github.io，站点地址就是 https://<用户名>.github.io。文件放仓库根目录，选 main 分支的 / (root)。

一个顺序上的坑：仓库是空的时候，Pages 设置页的分支下拉只有 None，Save 是灰的，上面写着「必须先有内容才能发布」。所以正确顺序是 先 push，再回来选分支。选完等一两分钟，构建完成才有内容。

最后

扒站改造的好处是快：版式、动效、三维场景都是现成的，你只需要关心「哪些内容是我的」。坏处是你会继承一堆你不理解的代码，所以每改一处，最好顺手在注释里写清楚为什么 —— 下次打开这个文件的人，大概率还是你自己。
